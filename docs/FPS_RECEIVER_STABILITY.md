# Просадки FPS и повторный запуск второго экрана

10 октября 2026. Установлены **Manager 0.9.4/build18** и **TV Display 0.7.3/code24**. Конкретное согласие на code24, сравнение 30/50/60 со звуком и повторный запуск получено. Этап 13 активен: короткие проверки проходят, полное устранение пользовательского дефекта на реальном видео ещё не подтверждено.

## Изменения

Mac допускает два подтверждаемых кадра в передаче вместо одного. Ожидание decoder admission больше не ограничивает поток одной RTT. Сохраняются порядок H.264 reference frames, отдельный deadline каждого PTS и ограниченные очереди: один encode, один ожидающий compressed packet, до двух отправок и последний незакодированный raw frame. При перегрузке заменяются только raw frames, закодированные P-frames не теряются.

Собственный виртуальный экран работает в60Гц. Для передачи30/50 выбираются свежие кадры по абсолютным PTS без накопления задержки. Поэтому «Захват Mac:60» при выбранных30/50 ожидаем; лимит относится к передаче. Idle samples и принудительные дубликаты счётчик не повышают. BGRA/queue5, hardware AVC, приоритет очередей и ProcessInfo activity действуют в пользовательском сеансе; activity освобождается при stop. Глобальное питание Mac не менялось.

ТВ использует MediaCodec callbacks на HandlerThread вместо timed polling. Настройка, подача, вывод и освобождение codec сериализованы на этом потоке. PRIORITY=0, FRAME_RATE и OPERATING_RATE сообщают штатному codec planner потребность; это подсказки API, а не гарантия FPS или изменение частот. ACK подтверждает queueInputBuffer, не показ кадра на панели.

Старая Activity очищает только свой published receiver; SSL socket получает reuseAddress до bind. Manager принимает две конкретные успешные предупреждающие строки am start, сохраняя отказ для остальных ошибок, timeout и усечённого вывода. Запуск доверенного peer можно повторно вооружить один раз после ограниченной проверки готовности. Фонового polling/reconnect нет; новый ключ требует прежнего подтверждения. REQUEST/LAUNCH/STATUS различаются в ошибке. Небезопасное владение receiver подтверждено кодом; причина каждого прежнего отказа и наличие TIME_WAIT не доказаны.

## Метод и результаты

Прежняя AppKit-полоса иногда давала около35 complete capture FPS при59 вызовах draw; повторный сеанс — около59. Без кодирования оба запуска захвата дали около59. Копии NV12/BGRA, пересоздание только SCK и интервал1/120 не устранили первый провал. Интервал1/60 дал более ровные55–56, но уменьшал захват относительно источника. Эти эксперименты не включены. Фокус окна не установлен как причина: непрерывный фоновый60с сеанс старого теста дал capture58.72/admission49.72 при target50.

Итоговая полоса движется средствами Core Animation, без перерисовки NSView на каждом callback и скачка в начало прохода. Display link считает только clock callbacks; выдачу compositor оцениваем по complete capture frames. Другой stimulus не позволяет приписать весь выигрыш одной оптимизации. Перед explicit --check есть8с для готовности нового UI; обычный старт этой паузы не имеет.

Каждый режим:1366×768, source/Quartz60Гц, два запуска с stop между ними,3с warm-up и30с измерения каждого сеанса. Включён system audio без mic; тихий stereo fixture воспроизводился через afplay. Все шесть сеансов оставались активными до stop, PCM отправлялся, ресурсы освобождались и собственный экран удалялся.

При60/audio encoder p95≈9.8–9.9мс, admission p95≈37.7–41.3мс; секундный приём не падал до15. При50/audio admission p95≈21.0–23.2мс. Меньший лимит даёт запас, но не гарантирует более плавный вывод: выбор50 из60 создаёт чередование интервалов, а admission cadence не равна Surface cadence. Ровные60 на панели не доказаны. Android11 не предоставил пригодные Surface callbacks; отсутствующее значение не считается нулём.

## Битрейт и ограничения

Технические данные показывают байты видеопакетов за интервал: AVC плюс framing/config, без audio/TLS/TCP overhead. Это не пропускная способность Wi-Fi. Для простой полосы в60/audio секундные значения≈0.49–1.31Мбит/с; encoder использует average bitrate, не постоянный CBR. Низкий битрейт простого кадра при неизменных capture FPS не доказывает урезание приёмника. Сложное полноэкранное видео на предельном битрейте не проверялось.

Плавность пользовательского видео/быстрого курсора, long-run, физический Surface cadence, sync с исходным звуком Mac и аудио после следующего standby остаются открытыми. Старый тест мог добавлять собственную неровность, но не объясняет все пользовательские просадки. Драйверы, clocks, thermal protection и настройки ТВ не менялись. Предыдущий аудит описан в [проверке второго экрана и звука](SECOND_SCREEN_AUDIO_AUDIT.md); закрытые ALSA/kernel/thermal данные не обходились.

## Завершение и проверки

Красной кнопкой закрыта активная1366×768/60 трансляция со звуком. Manager и его дочерний ADB завершились, виртуальный экран исчез. Выход ждёт очистки: через5с процессы ещё были, при следующей проверке после10с — отсутствовали. Read-only ADB подтвердил отсутствие TV receiver process/workers, установленный0.7.3/code24, прежние HOME/IME/data inode и timeout3600000мс. Глобальный ADB и чужие процессы не завершались.

Core/fake ADB/helper/doubles passed. Hardware AVC:48 generated frames во всех12 режимах/BGRA+NV12; held ACK проверяет credit1/2, compressed PTS order, latest raw и поздний ACK после stop. Android offline assembleLocalOptimized/checkStreamProtocol/lint passed:0errors,7warnings. Manager build/codesign и git diff --check passed. Установленный TV APK побайтно совпадает со сборкой; Manager executable и прежний сертификат проверены. Это не benchmark сложного видео.
