# Обрыв экрана при движении окна: Manager 0.6.4 / TV receiver 0.4.1

10 октября 2026. Пользователь сообщил: экран создаётся и виден на ТВ, но перенос окна или курсора приводит к обрыву. Также прямо поручил проверить общий движок в Manager и убрать отдельное Mac-приложение Display. Ранее пользователь разрешил устанавливать готовые обновления автоматически; UI/capture/runtime агентом в этом исправлении не запускались.

## Причина и доказательства

Создание и изображение подтверждены сообщением пользователя. Стабильность при движении не подтверждена. В ограниченной выборке журналов нет диагностического сообщения, которое устанавливает причину именно этого обрыва; прежний receiver скрывал исключение общим текстом. Падение процесса METZ по crash-report не подтверждено. Отсутствие ошибок в выборке не доказывает исправность.

В коде найдены два воспроизводимых пути преждевременной остановки:

- TV: `require(frames.offer(...))` сразу завершал сеанс при двух занятых местах очереди. Даже краткий перерыв декодера мог закрыть соединение и убрать виртуальный экран на Mac. При движении окна кадровая нагрузка возрастает; связь с конкретной попыткой остаётся гипотезой.
- Mac: callback VideoToolbox с успешным статусом и `frameDropped` вызывал fatal cleanup. [Документация Apple](https://developer.apple.com/documentation/videotoolbox/vtcompressionoutputhandler?language=objc) допускает пропущенный кадр без ошибки сжатия; наличие этого callback в пользовательской попытке не установлено.

Приоритет P1: прерывание основного сценария второго экрана. Уверенность высокая в дефектах кода, средняя в их объяснении пользовательского симптома. Реальные codec/сеть/capture/topology ошибки по-прежнему могут завершать сеанс.

## Исправление и единый Manager

- TV `FrameInbox` сохраняет лимит два кадра и порядок зависимых H.264 кадров. Вместо немедленного отказа ожидает свободное место до 500 мс; далее TCP ограничивает отправителя. При устойчивой перегрузке сеанс закрывается с точным кодом `FRAME_QUEUE_TIMEOUT`. Неограниченных очередей или выбрасывания отдельных P-кадров нет.
- Mac продолжает после успешного пропуска кадра, учитывает его в счётчике и запрашивает новый keyframe. Ненулевой OSStatus остаётся ошибкой. Сообщение отдельно различает кодирование, передачу и остановку захвата с числовым кодом, без сырых описаний/личных данных.
- Config JSON отправляется с сортированными ключами: текстовое сравнение конфигурации в прежнем receiver не должно зависеть от порядка JSON-полей.
- Receiver пишет только фиксированные стадии отказа `FRAME_QUEUE_TIMEOUT`, `STREAM_READ_OR_FORMAT`, `DECODER_CODEC`, `DECODER_BUFFER_OR_STATE`. Освобождение декодера защищено от вторичного исключения.
- Manager `build.sh` компилирует **те же** `DisplayApp`, `DisplayEngine`, `FramePipeline`, `StreamTransport`, `StreamProtocol`, `DisplayTopology`, `CaptureAccess` и `VirtualDisplay`, которые использовал standalone. Отдельной реализации экрана в Manager нет. Страница «Экран» использует этот встроенный движок непосредственно.
- Отдельный Mac Display оставлялся как резерв предыдущей пачки. По текущему поручению он убран из Applications и регистрации LaunchServices; сохранён только в игнорируемом приватном `.noindex` для возврата. В активных Applications/проектных build остался один METZ Manager 0.6.4.
- **TV METZ Display сохранён** как необходимый приёмник изображения и обновлён до 0.4.1/code6. Удаление Mac-дубликата не заменяет приёмник на телевизоре.

Условие 500 мс — защитный предел, не измеренная задержка. Увеличение очереди, прирост FPS, zero-copy всего тракта или исправление звука не заявляются.

## Проверки и установка

- Swift Manager core: authorization, history/partial snapshots, whitelist, parsing, fake ADB persistent channel, Unicode/CPU checks — passed.
- Swift Display core: framing/pins/NAL и различение успешного пропуска от codec error — passed. Objective-C adapter проверен только doubles, без настоящего виртуального экрана.
- JVM regression: заполненная очередь ждёт потребителя, сохраняет три последовательных кадра, ограничивает ожидание при постоянной перегрузке и очищается — passed. Protocol/pin/epoch/PTS checks — passed. Это тест очереди, не аппаратного декодера.
- Native Manager build и подпись — passed. Designated requirement совпадает с установленным 0.6.3; сертификат/Keychain/TCC не менялись.
- Receiver strict offline localOptimized build, JVM checks и lint — passed: 0 ошибок, 7 предупреждений. Новых зависимостей или инструментов нет. APK новой/прежней/rollback сборок имеют одинаковый сертификат.
- Manager0.6.4 и TV receiver0.4.1 установлены. Version readback и сохранение receiver data inode/HOME/IME/ADB проверены. Home, stock launcher, настройки сна, TLS-ключи не изменялись этой пачкой.
- Перенос окна/курсора, capture, полный TLS-видеосеанс, длительная стабильность и скорость агентом **не проверялись**. Исправление пользовательского обрыва ещё ожидает ручного результата.

## Возврат и следующий шаг

Прежние установленные Manager0.6.3/standalone0.4.3, исходники и TV APK сохранены в приватном `local/display-motion-diagnosis.noindex/`. Там же находятся карта перемещений и отчёты установки. Для TV собран исходный receiver0.4.0 с прежним сертификатом и повышенным code7 (`0.4.0-rollback`): адресная установка `-r` восстанавливает прежний код без downgrade или удаления данных. При применении code7 последующая новая версия должна иметь code выше7. Сам полный возврат не запускался; точность старых исходников и подпись проверены сборкой.

Для Mac — полностью закрыть Manager и восстановить сохранённый прежний bundle по приватной карте. При необходимости standalone также восстановить в прежнее место. Не сбрасывать разрешения или сертификаты ради возврата.

Ручная приёмка: Cmd+Q в Manager → открыть установленный Manager → «Экран» → на ТВ снова подтвердить приём → подключить → переместить курсор и одно окно → остановить. Если повторится отказ, сохранить точный новый текст и время; журнал теперь позволяет отличить перегрузку очереди от decoder/capture/transport ошибки. Агентский UI-тест требует отдельного разрешения.

Дорожная карта: исправление и консолидация Mac-приложений выполнены; этап13 остаётся активным до проверки движения окна/курсора и lifecycle. Полная приёмка Manager/Home, скорость и звук после standby остаются открытыми; следующий шаг — ручная проверка новой пары, затем оставшаяся финальная приёмка. Новый этап не вводится.
