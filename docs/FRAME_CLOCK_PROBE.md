## Установленное изменение

Production Capture→encoder теперь использует один отдельный deadline clock30/50/60. На каждом сроке он выбирает последнюю доступную capture surface; если обновления нет, подаёт повтор той же поверхности. Подача не ждёт следующего события ScreenCaptureKit. Первый выбор сдвинут на половину интервала более быстрого source/output clock (≈8,33мс при60Hz), чтобы не совпадать с callback захвата. PTS лежат на выбранной сетке, аудио сохраняет общий исходный origin; видео получает этот небольшой дополнительный стартовый запас. После задержки пропущенные такты учитываются и пропускаются: старые кадры не догоняются пачкой.

Память ограничена: одна latest source surface, один pending raw, один encode, один queued compressed packet и прежние1–2 transport credits. При перегрузке latest source продолжает обновляться, промежуточные pending raw заменяются. Compressed reference frames не выбрасываются и не переупорядочиваются. Stop/failure отменяет timer и освобождает latest surface; поздние ACK не меняют счётчики остановленного сеанса. Test fixtures сохраняют возможность подавать явные PTS без реального таймера.

Capture FPS остаётся фактическим темпом новых `.complete` samples. `fresh_encoded` и `repeated_encoded` отдельно учитывают новые samples и повторы после успешного hardware encode; сумма равна encoded count. `fresh_selected`/`repeated_selected` относятся к тактам, `pacing_skipped` — к просроченным тактам, `selection_skipped` — к source updates, объединённым до выбора. Новый numeric `pace` event связывает emission frame ID с source frame ID, PTS и lateness. В paced capture event выбор отложен до такта, поэтому поле `selected` отсутствует; encoded frame IDs относятся к emissions, `source_frame` связывает их с capture. Флаг repeated означает повтор одного capture sample, а не анализ содержимого картинки.

Диагностический текст показывает новые кадры захвата и повторы отдельно. Поэтому capture25/admission60 с35 повторами **не объявляется60 новыми кадрами движения**. Такая подача может уменьшить голодание decoder и bursty input, но не восстановит отсутствующие промежуточные изображения и не заменяет планирование показа на панели. TV по-прежнему использует immediate release; [Android MediaCodec](https://developer.android.com/reference/android/media/MediaCodec#releaseOutputBuffer(int,%20long)) предоставляет отдельный механизм presentation timestamp, в эту пробу не добавленный.

Первая clock-проба без фазового запаса показала опасное расхождение: при capture/admission/output≈60 из1083–1091 закодированных кадров315–348 были повторами. То есть средний output60 скрывал лишь≈40–43 новых capture samples в секунду. Это результат неудачной фазы выбора, а не подтверждение плавности. Точный прежний Manager20 был реально восстановлен и проверен, затем в рамках согласованной пачки добавлен sampling margin, Manager21 пересобран и установлен. Локальная регрессия с600 jittered source updates проверяет сохранение каждого source при таком запасе.

## Проверки, риск, возврат и следующий шаг

Manager build, Mac core/clock30–50–60/journal/doubles, Manager fake/helper,48 generated hardware frames/12 modes/reference-buffer1 и прежние credit/order/latest raw проверки прошли. Дополнительные generated clock checks проверили PTS grid, реальные повторы одной synthetic surface при отсутствии новых samples, переход к новому source, stale source rejection и прекращение работы после stop. Paced backpressure сcredit1/2 проверяет bounded backlog, выбор latest source, ordered PTS и поздние ACK. Четыре Python analyzer regressions сохраняют фактический capture FPS и отдельные repeat/late counters. Локальные hardware fixtures используют generated buffers; реальные capture/audio проверки описаны отдельно выше. Визуальная приёмка диагностического текста и субъективное качество звука остаются ручными.

Exact Manager0.9.6/build20 и исходники сохранены приватно `.noindex`, backup executable/signature проверены; точный возврат реально применялся между первой и исправленной clock-пробами. Для регрессии исправленной21 остаётся тот же проверенный возврат20. TV APK, драйверы, настройки, данные и transport protocol не менялись.

Риск: продолжение кодирования при idle увеличивает работу encoder и сетевой overhead; повтор кадра не гарантирует воспринимаемую плавность или ровные60 при нехватке ресурса. Приём/выход FPS включают явно отмеченные повторы. Журнал по-прежнему ограничен2×2МиБ/сеанс и8сеансами; дополнительные события могут раньше ротировать историю. Этап13 активен. Следующий шаг — пользовательский тот же видео/курсор сценарий с автоматическим журналом, затем различение source cadence, транспортных пауз и TV presentation scheduling. Фазовый запас проверен короткими сеансами; drift при долгой работе ещё не проверен.
