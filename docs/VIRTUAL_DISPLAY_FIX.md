# Создание виртуального экрана: Manager 0.6.2 / Mac Display 0.4.2

10 октября 2026. После адресного reset и ручного повторного подключения пользователь предоставил скриншот с ошибкой создания второго экрана. В текущем коде этот этап начинается после успешного запроса ScreenCaptureKit и готовности TLS-соединения с приёмником. Это продвижение по цепочке подключения; фактические кадры и декодирование ещё не подтверждены.

## Доказательства и уверенность

Локальная macOS: 27.0.1. Проверка **только метаданных Objective-C** обнаружила все четыре класса и нужные методы. Экран не создавался, методы приватных классов не вызывались, захват и UI агентом не запускались. Поэтому отсутствие классов не объясняет данный отказ.

Статически выявлены пробелы адаптера: задавался только `serialNum`, хотя в текущей системе есть и `serialNumber`; цветовые координаты не задавались явно; один synthetic ID использовался обоими Mac приложениями; ID проверялся до применения режима, а режим после снятия зеркалирования — без ожидания. Исходная общая ошибка не позволяла отличить отказ дескриптора, режима, регистрации или зеркалирования. **Какой из этих факторов вызвал наблюдаемый отказ, пока не установлено.**

Дополнительная проверка интерфейсов и рецепта дескриптора: [первичный код Chromium](https://chromium.googlesource.com/chromium/src/+/HEAD/ui/display/mac/test/virtual_display_util_mac.mm), просмотренная ревизия `be79514b3803c3b6078fa8d96022aa185ab4f940`. Здесь задаются оба serial-поля, ненулевой vendor и цветовые координаты. Это источник для проверки совместимости, а не результат запуска Chromium или доказательство исправления METZ.

## Изменения

- Дескриптор задаёт оба поддерживаемых поля одного ненулевого synthetic serial: Manager=2, standalone Display=1. Это собственные идентификаторы виртуальных экранов, не аппаратные номера пользователя.
- Явно задаются sRGB координаты, D65 white point и поддерживаемая rotation=0. Сохраняются 1280×720 / 30, SDR, отсутствие HiDPI. Поддержаны оба queue-setter варианта; optional поля вызываются только при наличии метода.
- Объявление mode width/height приведено к `unsigned int` по метаданным этой macOS. ID читается после успешного применения settings.
- Создание возвращает точный ограниченный код этапа, включая контролируемое исключение. Сырые детали исключения не раскрываются. Появление экрана и переход в финальный режим после снятия зеркалирования ждутся ограниченно, с отменой и освобождением принадлежащего приложению экрана.
- Успешная проверка приёмника обновляет оба сообщения готовности: прежние предупреждения о ключе/подготовке не остаются рядом с новой ошибкой создания.

## Проверки и возврат

Native core checks Manager/Display прошли. Новый Objective-C check использует только обычные NSObject doubles: modern/legacy queue, оба serial-поля, создание с ID после settings, девять стадий отказа, освобождение при ошибках. Он не разрешает и не создаёт настоящие виртуальные экраны. Обе Mac сборки прошли; используется тот же существующий сертификат и то же designated requirement. Разрешения, Keychain и TLS-ключи не менялись, TCC повторно не сбрасывался.

Установлены Manager0.6.2 и Mac Display0.4.2 по ранее выданному разрешению автоматически ставить готовые обновления. TV Home0.7/Display0.4 не изменялись. Предыдущие Mac bundles и исходники сохранены в приватном `.noindex`; source checkpoint хранится отдельно от пользовательской ветки/index. Для возврата — закрыть соответствующее приложение и восстановить сохранённый bundle. Сам возврат и полноценный видеотракт не проверялись.

Следующий ручной шаг: полностью закрыть Manager через Cmd+Q, открыть установленную версию и повторить подключение. Если отказ останется, новый текст покажет точную стадию. Проверки кадров/независимого рабочего стола/окон/курсора/удаления экрана и длительной стабильности остаются открытыми. Устранение звуковой проблемы после standby этим обновлением не заявляется.


## Следующая ручная попытка

Новый скриншот пользователя после установки 0.6.2 показывает «macOS не разрешила отдельный рабочий стол». По коду это стадия `.mirror`: собственный экран создан и активен; отказ относится к begin/configure/commit снятия зеркалирования или его итоговой проверке. Какой из четырёх путей сработал, пока неизвестно. Предыдущее исправление подтвердило продвижение до этого этапа, но полноценный второй экран ещё не работает.

Для точной изоляции подготовлен и скомпилирован приватный probe: один виртуальный экран с конфигурацией Manager, состояния до/после, коды транзакции, освобождение и проверка удаления. Только временное снятие зеркалирования принадлежащего probe дисплея, без записи/скриншотов/ввода/ТВ/постоянной конфигурации. Запуск ожидает отдельного согласия; сборка probe не является его выполнением. Дополнительное чтение текущей топологии без изменений: один online/active built-in main, без зеркалирования.


## Исправление регистрации: Manager 0.6.3 / Mac Display 0.4.3

После отдельного согласия пользователя выполнена ограниченная проверка создания, зеркалирования и освобождения на Mac. Несколько последовательных вариантов одного и того же probe изолировали C/Swift/оптимизацию/bundle context, по одному экрану за запуск; записи/снимков/ввода/подключения к ТВ не было. Установленные приложения агентом не запускались.

Подтверждённый дефект: для неизвестного ID текущая CoreGraphics возвращает `boolean_t = -1` из active/online/mirror/built-in queries (C unsigned-печать показывает 4294967295). Прежнее сравнение `!=0` принимало ошибку за истину. В узкой выборке журнала Manager присутствуют `Invalid display` после создания. Это объясняет ложную раннюю «активацию» и попытку снять зеркалирование до регистрации; конкретные begin/configure/commit коды прежней пользовательской попытки журнал не раскрыл. Объявлять общий запрет macOS на отдельный рабочий стол было некорректно.

Добавлен `DisplayTopology`: сначала актуальный online-list и присутствие ID, затем только корректные 0/1-флаги и размеры. Ошибка запроса не считается ни рабочим экраном, ни подтверждением его удаления. Создание, ожидание режима, наблюдение изменений и выбор существующего виртуального экрана используют этот адаптер. У транзакции зеркалирования теперь отдельные сообщения begin/configure/commit с кодом CoreGraphics. Также ограничен autorelease scope временных объектов фабрики; тесты doubles проверяют release без ожидания внешнего pool.

Новая реальная проверка с этим адаптером дала registered=true, active=true, mirrored=false, 1280×720, invalid-ID rejected=true и removed=true. После завершения снова один встроенный экран. Ранее raw-проверки показывали removed=false, поскольку повторное чтение уже удалённого ID тоже возвращало -1; это не доказательство утечки. Итоговый вывод об удалении основан на online-list.

Manager0.6.3 и Mac Display0.4.3 собраны и установлены с прежним designated requirement; предыдущие 0.6.2/0.4.2 bundles сохранены в приватном `.noindex` для возврата. Core и adapter tests прошли, сборки и signatures проверены. TCC/Keychain/TLS/ТВ не менялись. Подтверждены создание отдельного экрана и удаление в разрешённом probe; весь видеотракт, frames/декодирование/передача окон/длительная стабильность ожидают новой ручной попытки пользователя после Cmd+Q/reopen.
