# Первичная диагностика METZ Revive

**9 октября 2026, Europe/Prague.** Физический METZ; авторизованный ADB shell, без root. В активном приложении YouTube шло воспроизведение. Пользователь подтвердил: **звук нормальный**, для управления используется **atvTools на iPhone**. Это исходный срез обычного использования, а не idle baseline и не воспроизведение неисправности.

Подготовка и доступная диагностика чтением выполнены. Очистка, настройки, установки, перезагрузки, standby-циклы и UI-автоматизация не выполнялись. Причины Twitch-лагов и хрипа окончательно не установлены.

## Результат

1. `m5621`, 4 × Cortex-A53 до 1,3 ГГц, Mali-470 MP, 32-bit Android 11. Коммерческая маркировка SoC неизвестна.
2. Основной подтверждённый ресурсный предел — память: Android видит 907,2 МиБ, `meminfo` отмечает `critical`, zRAM занята примерно на 61%.
3. Есть конкретный дефект vendor-приложения: три падения `mtktvapi.agent` с отсутствующим классом управления громкостью. Связь со standby-хрипом не доказана.
4. Постоянная перегрузка CPU, перегрев, неисправность накопителя и отказ аппаратного декодирования не доказаны.
5. На `/data` свободно 2,15 ГиБ; проблема заполненного пользовательского накопителя не обнаружена. Службы Cast и Android TV Remote работают, но пользовательские сценарии не проверены.

Полные характеристики: [HARDWARE_PROFILE](../hardware/HARDWARE_PROFILE.md). Пакеты и проверенные кандидаты: [PACKAGE_INVENTORY](PACKAGE_INVENTORY.md).

CPU рассчитан по разности суммарных счётчиков `/proc/stat`, по всем четырём ядрам: busy = user + nice + system + irq + softirq + steal; idle и iowait показаны отдельно. Первые кадры `top` заметно зависят от интервала и накладных расходов самой диагностики; не использованы как доказательство длительного 100% CPU. Интервалы приходятся на разные моменты видео и не являются строго сопоставимым benchmark.

В `meminfo` основные PSS: YouTube 142915 КиБ, system 68445, GMS 57432, launcher 46656, TV provider 30052, Cast 22730, atvTools helper 22317, recommendations 17088, Anoki 12496. Это значения, сообщённые dumpsys, а не обещанный объём RAM, который освободится после отключения. PSS, RSS, swap, kernel и Lost RAM нельзя складывать без учёта их методик. Различия RSS/PSS здесь не считаются доказательством утечки.

## Найденные проблемы

### 1. Малый запас RAM при обычном воспроизведении

- **Обнаружено / доказательства:** `critical` в `meminfo`, ~306 МиБ в swap при общем ~500 МиБ; ~110 МиБ физически использует zRAM. Low-RAM mode уже включён.
- **Вероятная причина:** ограниченная память плюс совместное присутствие YouTube, Google services, штатного HOME, рекомендаций и vendor-процессов.
- **Уверенность:** малый ресурс и состояние `critical` подтверждены; причинная связь с каждым зависанием и интенсивный swap-thrashing требуют проверки. Доступные vmstat не содержат нужных swap-rate counters; PSI отсутствует.
- **Влияние:** вероятны повторные загрузки приложений и задержки reclaim. Конкретные LMK kills в короткой выборке не обнаружены.
- **Решение:** уменьшать только ненужную резидентную нагрузку по одному кандидату; лёгкий launcher оценивать позже, после сохранения штатного HOME.
- **Риски / восстановление:** ошибочное отключение нарушит TV/ввод/рекомендации; сохранить исходное enabled-state и подготовить точный возврат до применения.
- **Приоритет:** высокий.

### 2. Падения `mtktvapi.agent` при загрузке receiver

- **Обнаружено / доказательства:** 3 `FATAL EXCEPTION: main`; процесс `mtktvapi.agent`, `NoClassDefFoundError` / `ClassNotFoundException` для `com.mediatek.twoworlds.tv.MtkTvVolCtrlBase`; стек `MyIntentReceiver.<init>(MyIntentReceiver.java:48)`.
- **Вероятная причина:** несовместимость старого vendor-APK с доступностью framework-класса. Agent версии 1.0 имеет targetSdk 23; библиотека `com.mediatek.twoworlds.tv` зарегистрирована, но не указана в его `usesLibraries/usesLibraryFiles`. Возможны дефект library visibility или изменение содержимого библиотеки. Содержимое класса не проверено.
- **Уверенность:** падения и отсутствующий в classloader класс подтверждены; ошибка упаковки/сборки вероятна. Причина хрипа не подтверждена.
- **Влияние:** часть vendor-обработчиков событий не выполняется; точный охват громкости/CEC/power не установлен.
- **Решение:** уточнить совместимую официальную сборку у METZ и назначение receiver. Не подменять framework JAR и не отключать agent с системным shared UID 1000.
- **Риски / восстановление:** sideload несовместимых компонентов может сломать функции TV; гарантированного отката прошивки сейчас нет.
- **Приоритет:** высокий для дальнейшего исследования.

### 3. Хрип после standby — причина пока неизвестна

- **Обнаружено / доказательства:** повторяемый сценарий сообщён пользователем; в текущем сеансе звук нормальный, underrun-счётчики микшера 0/0.
- **Вероятная причина:** остаются HAL/драйвер resume, clock/buffer state, DSP либо усилитель/питание. Выбрать один вариант по этому снимку нельзя.
- **Уверенность:** пользовательский симптом; гипотезы требуют аварийного снимка.
- **Влияние:** искажение звука во всех приложениях по сообщению пользователя.
- **Решение:** при естественном появлении хрипа собрать профиль `audio` до reset/перезагрузки/отключения питания; сопоставить маршрут, частоты, underruns и power state.
- **Риски / восстановление:** сбор чтением не требует отката. Перезапуск audioserver и firmware hacks не рекомендованы; аппаратная неисправность не исключена.
- **Приоритет:** высокий.

### 4. Задержки atvTools и Twitch — неисправность не воспроизведена

- **Обнаружено / доказательства:** пользователь назвал atvTools; его helper 1.4.1 установлен и процесс присутствует. [Описание разработчика](https://atvtools.app/) связывает работу с USB/Network debugging и ADB-командами. Для atvTools основной transport — ADB; точный путь каждой кнопки/helper-команды не трассирован. Наличие Android TV Remote на 6466/6467 не доказывает использование этого другого протокола atvTools.
- **Вероятная причина:** возможны reconnect/discovery на iPhone, Wi-Fi jitter, задержка ввода/отрисовки и memory reclaim. Для Twitch ещё возможны выбранное качество, codec, сеть и приложение.
- **Уверенность:** кратковременный сетевой jitter подтверждён; причинная связь с жалобами требует измерений. Mac ADB быстро отвечает, что не исключает отдельной проблемы iPhone.
- **Влияние:** задержки управления и видео заявлены пользователем, в текущем срезе не оценены.
- **Решение:** короткие согласованные сценарии ниже; защищать atvTools/helper, ADB и сеть при очистке.
- **Риски / восстановление:** сетевые перестройки или выключение сервисов могут лишить управления. Сначала USB-клавиатура и исходные настройки; никаких изменений в этом этапе.
- **Приоритет:** средний для измерений; Twitch — высокий по пользовательскому влиянию.

## Рекомендации A / B / C

### A. Обратимые кандидаты после согласования

| Действие | Основание / ожидаемый эффект | Риск, проверка и возврат |
|---|---|---|
| Сравнить 720p30 с текущим качеством одного и того же потока | Android выводит 720p; снизить объём декодирования/буферов. Польза не измерена | Меньше детализации/плавности; сравнить dropped frames и RAM; вернуть исходное качество |
| Уменьшить ненужные каналы рекомендаций штатными настройками HOME | Recommendations занимает память, пользователю не нужен такой контент | Не гарантирует удаления рекламы и экономии RAM; записать исходные каналы, проверить HOME, вернуть настройки |
| Рассмотреть только подтверждённо ненужное пользовательское приложение | На момент среза использование TCL Browser и Kick было неизвестно. Позднее пользователь подтвердил использование обоих, затем отдельно разрешил удалить TCL и заменить браузер | Kick сохранён; выполненная замена браузера описана в recovery plan. Изменение не доказывает экономию RAM или ускорение |

Во время первичного среза приведённые действия не применялись. Последующая адресно согласованная замена браузера описана в [плане восстановления](../recovery/RECOVERY_PLAN.md). Формально обратимое действие не становится автоматически полезным: эффект проверяется в сопоставимом сценарии.

### B. Требуется дополнительная проверка

- Anoki ACR, recommendations, launcher customizer и demo: проверить receivers/providers/shared UID и роль в HOME/Live TV. UID 1000 или `PERSISTENT` — причина особенно внимательно исследовать, а не разрешение отключать.
- Штатный Cast: receiver и Warg services присутствуют, порты 8008/8009/8443 слушают; Chrome casting, звук, возврат управления и память после остановки ещё не проверены.
- HDMI CEC/ARC, Game/Energy Saving modes: CEC уже включён, ARC заявлен у HDMI 1; список реально доступных picture modes конкретного экземпляра и input lag не проверены. Не предлагать «включить CEC» как найденное новое улучшение.
- Thermal и standby: Android HAL не предоставляет температуры, kernel/sysfs закрыты; требуется vendor-supported путь чтения либо внешние измерения. Без этого не обещать экономию электричества.
- Agent/framework совместимость и прошивка: нужна официальная сборка под модель, регион, board и ревизию. В просмотренных официальных материалах совместимый recovery/USB image не найден; это не доказательство отсутствия обновлений у поддержки.
- zRAM/governor/LMK: текущий zRAM работает, governor штатный `interactive`; данных для смены параметров недостаточно. Low-RAM flag уже активен.

### C. Не применять

Разгон, фиксированный `performance`, thermal-disable, voltage tweaks, root/bootloader unlock, подмена HAL/JAR, случайная прошивка, отключение zRAM, увеличение swap без измерений, task killers, автоматическая очистка RAM/кеша, debloat-листы из интернета и отключение Cast/ADB/сети/ввода/аудио/vendor TV служб. Ни один такой шаг не обоснован этим исследованием; для части из них восстановление не гарантировано.

## Точечные сценарии следующего наблюдения

Эти проверки **не выполнены**. Агент не управляет UI без отдельного разрешения. Пользователь может выполнить обычные действия вручную; дальнейший ADB-сбор делать по явному запросу, без фонового расписания.

### Звук при естественной неисправности

1. Не создавать искусственных power/standby-циклов. При следующем хрипе записать длительность standby, приложение, маршрут (динамики/наушники/HDMI), громкость и факт искажения в другом уже используемом приложении.
2. До изменения состояния собрать `--profile audio --label distorted-audio` (пример команды в README). Нормальный эталон уже сохранён: `initial.json`, audio-поля.
3. Сравнить sample rate/format, mixer underruns, HAL dump, маршруты и power/logcat. Отсутствие underruns не исключает аналоговый тракт.
4. Программную перезагрузку и сравнение с физическим отключением питания рассматривать отдельно, только после согласия; в этой диагностике их результат неизвестен.

### Twitch, 60–90 секунд обычного просмотра

Зафиксировать трансляцию, выбранные resolution/FPS/bitrate и доступную статистику dropped frames/buffer, затем запросить один профиль `video`. При лаге сравнить CPU/memory и конкретный codec. Буферизация без frame drops и с сетевым ожиданием отличается от decode/render lag, но показатели должны быть измерены. Второе качество сравнивать на том же потоке после согласования. YouTube-снимок не переносить на Twitch.

### atvTools, Cast и HDMI

- atvTools: отдельно измерить время до соединения и задержку после уже установленного соединения; сравнить обычную навигацию с USB-клавиатурой. Никаких циклов standby ради теста. Не отключать helper; пробу других протоколов не считать уже проведённой.
- Cast: вручную начать обычную Chrome-трансляцию, проверить видео/звук и отзывчивость, остановить и проверить освобождение ресурсов. Только тогда решать, нужен ли собственный receiver.
- HDMI: подключить Mac вручную, записать предлагаемые macOS/TV разрешения и частоты. Android framebuffer не является таблицей HDMI input modes. CEC переключения и input lag требуют отдельного согласованного теста.

## Сбор, инструменты и публикация

Git 2.50.1, ADB 36.0.2 / protocol 1.0.41, Python 3.9.6 и gh 2.89.0 доступны. Swift/Xcode CLI paths присутствуют; полноценность Android/macOS build toolchain не проверялась, поскольку приложения пока не разрабатываются. Ничего не установлено. Специализированного Android TV diagnostics skill в доступном каталоге нет; отдельный skill не нужен для этого сбора.

Raw-данные остаются в игнорируемом `local/diagnostics/`: `initial.json`, `focused.json`, `context.json`. Источники CPU: `load_interval` и `vm_counters`; памяти: `memory`, `memory_processes`; ошибок: `crash_history`, `agent_libraries`; сети: `network`, `connections`, `adb_roundtrip_ms`, `ping`. Первые `media`/`network` outputs обрезаны на 256 КиБ; необходимые codec files/сервисы получены отдельными узкими чтениями. Ошибки `Permission denied` относятся к закрытым диагностическим интерфейсам, а не доказывают неисправность оборудования.

`dmesg` недоступен, хотя shell-pipeline завершился кодом 0 из-за успешного `tail`. Это учтено по stderr. Kernel I/O errors и износ накопителя оценить нельзя. Все сохранённые raw-снимки приватны; в публичных документах нет LAN-адресов, SSID/MAC, серийных номеров и персональных логов.

Локальные safety-тесты сборщика проходят (6): ограничение двух потоков вывода, timeout с сохранением частичных данных, запрет сбора с unauthorized target, сохранение существующего снимка, права 0600/явный target, защита пути метки. UI и аппаратные сценарии этим не проверяются.

GitHub remote доступен для чтения и push через существующий Git credential helper; GitHub-коннектор имеет права push/PR. Сам CLI `gh` не авторизован, но его авторизация не нужна при этом способе публикации. Пользователь 2026-10-09 разрешил push/PR без повторного подтверждения; ветка `codex/initial-diagnostics`, base `main`. Raw-снимки и локальные настройки в публикацию не включаются.

Справочная интерпретация давления памяти: [Android TV memory guidance](https://developer.android.com/training/tv/playback/memory). Документ объясняет возможное влияние reclaim на кадры, но не доказывает причину конкретного лага на этом устройстве.
