# Звук и задержки управления — исследование этапа 6

9 октября 2026. Пользователь сообщил: звук сейчас нормальный; управление иногда тормозит именно с телефона через atvTools. Исследование чтением ADB начато по команде «дальше», пока ручная оценка пачки этапа 5 остаётся открытой. Это не завершение исправления всех симптомов.

atvTools использует ADB через Wi-Fi по [описанию разработчика](https://atvtools.app/). Наличие Android TV Remote на других портах не доказывает использование его протокола этой кнопкой. Версия приложения на iPhone и настройки mirroring неизвестны; helper 1.4.1 — другой компонент.

Накопленные задержки HOME дают основание исследовать отрисовку, но не позволяют выбрать единственную причину телефонного зависания. Возможны задержки Wi-Fi/reconnect, пробуждение helper из памяти, обработка ввода или отрисовка. Причинная связь с отключением Recommendations также не доказана: сопоставимой статистики до него нет. Значение `High input latency` относится к графическому конвейеру, а не к измерению сети iPhone. Метод чтения кадров описан в [Android dumpsys](https://developer.android.com/tools/dumpsys#gfxinfo).

## Дефект vendor agent уточнён

1. Crash buffer содержит те же три падения `mtktvapi.agent` с `NoClassDefFoundError` / `ClassNotFoundException` для `com.mediatek.twoworlds.tv.MtkTvVolCtrlBase`, в конструкторе `MyIntentReceiver`, строка 48. Дополнительного падения в свежей короткой выборке нет.
2. PackageManager и `/vendor/etc/permissions/libs_permissions.xml` регистрируют `com.mediatek.twoworlds.tv` по пути `/system/framework/com.mediatek.twoworlds.tv.jar`.
3. Чтение этого точного пути возвращает **No such file or directory**. Проверенные альтернативные пути в `/vendor/framework`, `/system_ext/framework` и соответствующие oat-файлы также не найдены. Это не доказывает отсутствия всех возможных реализаций класса в прошивке.
4. Agent APK — 37 844 байта, версия 1.0, targetSdk 23. Manifest не содержит `uses-library`; runtime `usesLibraries/usesLibraryFiles` тоже не включает эту vendor-библиотеку. В DEX есть ссылка на класс, но определены только четыре класса самого agent, без `MtkTvVolCtrlBase`. Временная копия APK удалена после локального анализа.

**Вывод:** подтверждена несогласованность регистрации библиотеки и файлов текущей сборки; отсутствующая/неподключённая зависимость — обоснованное объяснение данного падения. По [документации Android](https://developer.android.com/guide/topics/manifest/uses-library-element) `uses-library` подключает код shared library к classloader приложения. Точная история дефекта сборки и связь со звуком/телефонными задержками не установлены.

Agent имеет shared UID 1000 и vendor-обработчики громкости/power/TV. Отключение receiver, подмена JAR, переподпись APK или root не являются проверенным исправлением. Точное соответствующее обновление производителя и возврат прошивки пока не найдены. Подготовлены сведения для будущего обращения: модель и fingerprint в [аппаратном профиле](../hardware/HARDWARE_PROFILE.md), исключение, путь библиотеки и manifest-факты. Сообщение производителю не отправлялось.

## Следующее наблюдение

Новый профиль `remote` в [сборщике](../../scripts/collect_diagnostics.py) выполняет 11 ограниченных последовательных чтений: identity, power, ошибки, RAM, CPU-интервал, foreground, ввод, last ANR, helper, Wi-Fi и HOME framestats. Helper дополнительно определяется через `pidof` и читается по PID: shell-процесс может отсутствовать в app registry. Сбор не нажимает кнопки, не запускает приложения, не делает screenshots, не очищает логи/статистику и не работает постоянно. Последовательный сбор занимает время и сам добавляет небольшую нагрузку; это не трасса каждой кнопки.

```sh
# При естественном появлении задержки; новую метку выбирать для каждого снимка
python3 scripts/collect_diagnostics.py --serial '<текущее устройство>' --profile remote --label phone-lag-01

# При естественном появлении хрипа, до изменения состояния
python3 scripts/collect_diagnostics.py --serial '<текущее устройство>' --profile audio --label distorted-audio-01
```

Пользователь исключил сравнение пультов из обязательных шагов; оно не выполнено. По исходному брифу физического пульта нет, резервное управление — USB-клавиатура. При естественной задержке можно сообщить время/приложение и сохранить состояние для чтения remote, но ожидание такого случая не блокирует независимую локальную разработку METZ Home. Хрип/Twitch остаются открытыми наблюдениями; принудительный standby/запуск потока агентом не выполнялись.

Следующая самостоятельная разработка — лёгкий [METZ Home](../../metz-home/README.md) с сохранённым штатным HOME и отдельной последующей проверкой. Исторический jank даёт основание для такого эксперимента, но не доказывает, что замена launcher устранит именно телефонную задержку.

## Изменения и проверка

В этом исследовании настройки и пакеты ТВ не изменялись. Recommendations остаётся enabled=3, Anoki enabled=0; [проверенный откат](PERFORMANCE_PLAN.md) сохранён. Этап 5 ждёт ручной оценки HOME/уведомлений/лишнего контента и сопоставимых замеров.

Финальный профиль `remote` выполнен на ТВ: все 11 команд exit=0, без timeout/truncation. Первая проба общего профиля показала закрытые `/proc/swaps`, diskstats и zRAM; в целевом remote оставлены доступные необходимые чтения. 12 локальных тестов прошли, включая отсутствие input injection/reset в remote, защиту существующих снимков и безопасный возврат пакетов. Тесты используют подмену ADB, UI не запускают.

Приватные доказательства: `known-problems-current.json`, `known-problems-followup.json`, `vendor-library-check.json`, `vendor-agent-static.json`, `remote-normal-final-20261009.json` в игнорируемом `local/diagnostics/`, права 0600. Сырые логи, APK и идентификаторы сети не публикуются. Фоновый мониторинг и новые зависимости не создавались.

## Новое проявление после standby — 9 октября 2026

**Сообщение пользователя:** ТВ был выключен и включён; звук стал плохим/глухим через встроенные динамики во всех приложениях. Для наблюдения открыт YouTube. Это новое проявление после ранее нормального звука; прежние спокойные снимки его не опровергают.

**Проверка чтением:** первый audio snapshot попал на отсутствие активных дорожек (Standby yes), поэтому не использован как доказательство воспроизведения. Повторный ограниченный снимок подтвердил YouTube в foreground, активную его дорожку и Standby no.

| Доказательство | Результат | Что это означает |
|---|---|---|
| Активный mixer | speaker, 48 000 Гц, два канала; master volume 1, balance 0 | Маршрут на встроенные динамики подтверждён, смещение баланса не видно |
| Audio track/mixer underruns | 1 активная дорожка YouTube; track 0, mixer partial=0/empty=0 | В момент снимка не зарегистрирован недокорм буфера; тембр/искажение сигнала этим не измерены |
| AudioFlinger effects | 0 Effect Chains | Android effects не видны; это не отключение обработки vendor DSP/HAL |
| Settings global | sound_surround=1, sound_sound_surround=1, sound_bass=70, sound_treble=88, sound_balance=0 | Сохранённые vendor-настройки доступны. Шкала, значения по умолчанию и фактическое применение после standby не установлены |
| Сохранённый EQ | sound_equalizer=0; полосы 120/500/1500/5000/10000: 26/15/31/36/44 | Эти числа не объявлены активной характеристикой EQ; значение режима и происхождение неизвестны |
| Состояние питания | Awake; зарегистрирован предыдущий sleep с power_button | Симптом после пробуждения соответствует сообщению пользователя; причинная связь с DSP не доказана |
| Ограниченная выборка logcat | Совпадений audio/mtktvapi в новом фильтре нет | Отсутствие строк не доказывает отсутствие дефекта |
| Доступ | AudioService/Flinger/Policy прочитаны; `/proc/asound/*` недоступны | Kernel/ALSA и акустический выход не проверены; SELinux/root не обходились |

**Причина:** пока не установлена. **Гипотеза с невысокой уверенностью:** профиль обработки/восстановление vendor audio после standby; общая проблема во всех приложениях делает изолированный дефект YouTube менее вероятным. Возможность аппаратного дефекта динамиков/усилителя чтением ADB не исключена. Нельзя связывать проблему с отключёнными Recommendations или прежним vendor crash без нового доказательства.

**Влияние/приоритет:** неудовлетворительный звук во всех приложениях по сообщению пользователя, P1 для следующей проверки. **Решение:** получить контролируемую ручную пробу одного и того же ролика в текущем профиле и стандартном профиле/без surround, записав исходный экран настроек и результат. Смена профиля, сброс звука и перезагрузка в этой работе не выполнены; автоматическая «починка» не заявлена. **Риск/откат:** изменения vendor settings через ADB могут не синхронизировать DSP; поэтому не записывались. Для будущей согласованной пробы вернуть именно исходный профиль/значения в штатном меню, а не неизвестные заводские числа.

Оба raw-снимка и исходные sound settings сохранены приватно в local; в Git включена только эта очищенная сводка. Профиль `audio` теперь также читает foreground и фиксированные vendor sound keys, что позволит сравнить повторное проявление без полного чтения всех настроек.

## Повторное сообщение в этапе 12

Пользователь подтвердил: проблема со звуком есть прямо сейчас; Cast/Manager проверит в самом конце. Новый ограниченный audio срез завершён (10 команд), но **активных дорожек 0, Standby yes**. Поэтому он не используется как проверка тембра во время воспроизведения или как доказательство исправления. У memory/audio_service сохранены ограничения доступа, включая закрытый kernel ALSA.

12 общих сохранённых sound keys совпали с прежним приватным снимком; изменений нет. Это не доказательство одинаковой фактической обработки DSP после standby. После ответа пользователя «играет» второй ограниченный audio срез подтвердил YouTube/speaker, 1 активную дорожку, Standby no, 48 кГц/stereo, mixer underruns 0/0, balance0, Android effect chains0. Memory/audio_service по-прежнему имеют ограничения доступа. Тембр/аналоговый выход этим не измерены, причина остаётся открытой.

На предложенную ручную пробу выключить Surround пользователь ответил: «нету разницы ни в каких настройках». Точный перечень всех изменённых параметров неизвестен; это не доказательство отключения фактического vendor DSP. Гипотеза Surround как простого исправления стала слабее. Настройки, приложения, аудиосервис и питание агент не переключал.

После отдельного прямого согласия выполнена **одна обычная программная перезагрузка**. Read-only preflight 4/4 сохранил сборку, ADB=1, штатный HOME, Awake и текущие sound keys; reboot exit0. ADB кратко был offline после первого ответа, затем самостоятельно восстановился после паузы не менее 60 секунд. Повторного reboot/сброса ключей или сети не было. Пять post-read команд прошли: boot_complete1, uptime около179 секунд, сборка/ADB/default HOME/sound keys совпали с исходными, Home0.3.0 сохранён.

Ответ пользователя после перезагрузки: **«стало лучше»**. Это подтверждённый ручной результат разовой меры; причина и полная нормализация во всех источниках/после следующего сна не установлены. Улучшение при неизменных сохранённых настройках поддерживает гипотезу временного состояния audio после пробуждения, а не простого выбора Surround. Связь с прежним vendor agent exception не доказана; аналоговый тракт не исключён. Автоматических перезагрузок/сброса звука/прошивки не создано. [Итоговый статус этапа 12](../FINAL_STATUS.md) сохраняет дефект открытым и отделяет его от прошедших локальных build/tests.
