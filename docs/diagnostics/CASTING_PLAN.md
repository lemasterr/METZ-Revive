# Этап 8 — штатный Cast

Начат по прямому запросу пользователя 9 октября 2026. Приоритет — беспроводной экран Mac, затем фото/видео и iPhone; HDMI остаётся резервом. Сторонний приёмник на телевизор не установлен. Собственный Chromecast/AirPlay receiver не реализуется без необходимости и анализа ограничений.

## Подтверждённая готовность

- `com.google.android.apps.mediashell` 3.72.446070 установлен, включён, процесс работает. Активны CastReceiverService и WargService.
- TCP listener на 8008/8009/8443 найден. С Mac получен HTTP 200 на DIAL `device-desc.xml`, модель METZ 2K TV.
- За ограниченный интервал обнаружено mDNS `_googlecast._tcp`; объявление сопоставлено именно с этим ТВ по DIAL identity, сервис разрешился на 8009. Raw identity/адреса не публикуются.
- Chrome на Mac установлен, версия 154.0.8037.98; macOS27.0.1. Разрешения Local Network / Screen Recording через UI не проверялись и не менялись.
- Новый диагностический профиль `cast` испробован: все 9 команд завершились без timeout/truncation. Снимок собирает package/services/process/listeners, RAM, Wi-Fi, media metrics и ограниченный фильтр logcat. Он не открывает receiver, не отправляет LOAD/STOP и не вводит клавиши.

Это подтверждает доступность приёмника и обнаружения. Реальная передача, декодер сеанса, звук, задержка, RAM и восстановление после сна **ещё не проверены**. В коротком снимке media metrics нет нового подтверждения аппаратного AVC-декодирования; прошлое VP9-видео YouTube не доказывает аппаратное декодирование будущего Cast-сеанса. Короткий logcat также не удостоверяет отсутствие дефектов.

## Доступные сценарии

| Сценарий | Первый путь | Ограничения / проверка |
|---|---|---|
| Весь экран Mac | Chrome → Cast → Sources → Cast screen → METZ | Встроенное зеркалирование. Системный звук может остаться на Mac; задержка пока неизвестна |
| Видео/звук вкладки | Chrome → Cast tab либо кнопка Cast сайта | Google рекомендует вкладку, если звук нужен на ТВ |
| Локальное фото/видео Mac | Открыть файл через Cmd+O в Chrome, передать вкладку | Совместимость конкретного файла проверить. Не копировать файл постоянно на ТВ; локальный file:// не передавать как URL для receiver |
| iPhone: YouTube и другие Cast-приложения | Кнопка Cast внутри приложения | Приложению нужен доступ Local Network; конкретное приложение должно поддерживать Cast |
| iPhone: произвольные фото/видео | Сначала проверить имеющееся приложение с Cast; иначе отдельный sender | Копирования всего экрана iPhone средствами обычного Cast не считаем подтверждённым |
| iPhone/Mac: AirPlay screen mirroring | Требуется совместимый AirPlay receiver | Наличие Google Cast не доказывает AirPlay. Поддержка этого ТВ не подтверждена; рекламный приёмник не устанавливается |

## Следующая ручная проба

1. Mac и ТВ в одной домашней сети. Если Chrome запросит Local Network и запись экрана — разрешить нужный доступ самому. Защиту/файрвол целиком не отключать.
2. Передать одну вкладку с обычным видео, проверить изображение и звук, завершить через Chrome.
3. Передать экран Mac с движущимся окном/скроллом. Отметить субъективную задержку отдельно от успешного соединения; измерение миллисекунд требует отдельного протокола, а ADB ping им не является.
4. Открыть локальную фотографию и короткий MP4 H.264/AAC через Cmd+O, передать вкладку; проверить звук/синхронизацию. Это стартовый совместимый формат, не гарантия поддержки любого profile/level.
5. Проверить Cast из YouTube на iPhone и штатный возврат на HOME. Результат: что работает, какой сценарий не работает, звук на Mac или ТВ, зависания/разрывы.

Эти шаги — ручной чек-лист, не выполненный агентом UI-тест. Экран/файлы пользователя не захватывались. Агент не запускал сеанс и не менял разрешения macOS. При естественном дефекте можно снять профиль чтением, не прерывая передачу:

```sh
adb devices -l
python3 scripts/collect_diagnostics.py --serial '<текущее устройство>' --profile cast --label cast-during-problem
```

Сначала сравнить с новым спокойным снимком. Raw хранится только локально с ограниченными правами. Коды возврата и ограничения capture не заменяют анализ содержимого.

## Решение о собственной передаче

Для первой пробы подходит уже работающий встроенный Cast. Его возможности нужно оценить раньше установки дополнительной службы на ТВ с примерно 907 МиБ доступной Android RAM и Wi-Fi 2,4 ГГц. Link rate не равен полезной пропускной способности или задержке. Стартовая цель собственного потока при необходимости — 1280×720/30, H.264 с аппаратным кодированием Mac и аппаратным MediaCodec на ТВ; это проектное предложение, а не применённая оптимизация.

Если реальная проба покажет достаточную картинку/звук/задержку, отдельный receiver не нужен. Если нужен прямой показ локальных медиа с iPhone, следующим решением может быть sender для штатного Cast. Если приоритетный экран Mac не удовлетворит по задержке/звуку, оценить ScreenCaptureKit + VideoToolbox → ограниченный поток → MediaCodec + SurfaceView, проверив права macOS, доступный аппаратный AVC, transport/backpressure, RAM, аутентификацию сеанса и зависимости. WebRTC — кандидат, не выбранная библиотека. Свой Cast/AirPlay протокол не обещан.

Сеанс штатного Cast прекращается кнопкой Stop в sender. Постоянные media-файлы на ТВ агент не создавал, фоновые процессы или настройки для этого этапа не добавлял; системный Cast сохранён. Следующий результат этапа — реальная ручная проба и решение по её ограничениям, затем этап 9 METZ Manager.
